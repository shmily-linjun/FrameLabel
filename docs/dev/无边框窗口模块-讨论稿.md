# 无边框窗口模块（Frameless Window）讨论稿

> 状态：**已实现 M1–M3（fork.7，2026-11-18）**。本文保留冻结的设计与决策基线，实施偏差见 §11；后续调整需按 §12 记录。
> 关联：`docs/开始.md` T7、`docs/dev/CODE_STRUCTURE_REPORT.md` 的窗口/工具栏结构、`CHANGELOG-fork.md` 的 fork.4–fork.7 记录。
> 背景：fork.4 的登录入口曾占用画布一行；fork.6 已改为菜单栏右上角 corner widget + 状态栏归属文字。本文评估更进一步的方案：自绘无边框标题栏，并把菜单、软件名/图标、标题栏按钮合并到同一区域；目标是形成一个**可被其他项目直接复用**的独立模块。

---

## 1. 目标

1. 提供一个不依赖本项目业务代码的 `FramelessWindow` 模块，其他 PyQt6 项目可以复制/依赖后直接使用。
2. 合并原生标题栏与菜单栏，减少一条窗口 chrome 的高度；把登录、侧边栏显隐等“应用级按钮”放到标题栏右侧。
3. 保留用户对原生窗口的既有预期：拖动、四边/四角缩放、双击最大化、最小化/最大化/关闭、贴边吸附、多显示器与高 DPI、任务栏行为。
4. 允许通过**启动配置**回退原生边框，便于出问题时降级；不做运行中切换（见 §2.1）。

## 2. 非目标

- 不做跨平台像素级一致；Windows 为其主目标平台，Linux/macOS 保证可用即可。
- 不复刻 Win11 的全部 Snap Layouts 细节（**已确认接受退化**，见 §2.1）。
- 不在本模块内实现业务菜单内容；只提供“如何放置菜单/按钮”。
- 不改动标注、训练、导出等业务逻辑。
- **不提供运行中的无边框/原生切换**（2026-11-18 确认），回退通过启动配置重启完成。

## 2.1 已确认决策（2026-11-18）

| # | 问题 | 决策 | 设计影响 |
|---:|---|---|---|
| 1 | Win11 Snap Layouts 悬停提示 | **接受退化** | 不实现 `HTMAXBUTTON` 原生提示，省 1–2 人日；文档声明该退化 |
| 2 | Linux/macOS 默认形态 | **默认无边框**；macOS **接受实机验证后可能退回原生或“透明标题栏”** | 平台默认值由模块提供，宿主可覆盖；macOS 保留降级路径 |
| 3 | 回退方式 | **不允许运行中切换**，启动时按配置决定 | 启动时二选一：只创建一套窗口 chrome，不会出现两组最小化/最大化/关闭按钮 |
| 4 | 菜单溢出 | 折叠为“**更多 »**” | 模块实现溢出菜单，优先保证标题栏按钮不被挤压 |
| 5 | 菜单显隐 | 右键菜单栏空白处 → 勾选显示/隐藏顶层菜单，状态持久化 | 新增 `menu_visibility_changed` 与持久化钩子 |
| 6 | 模块位置 | `anylabeling/widgets/frameless/`（新建包） | 不放进 `views/labeling`，保持与应用级 chrome 同层 |
| 7 | 菜单层级 | **支持三级及以上**；动态菜单约 5 条 | 用 `QMenu` 嵌套；动态列表建议设上限（见 §3.1） |
| 8 | 主题切换 | **重启生效**（与现状一致） | 模块启动时 `apply_theme()`，不需要运行时重设 |
| 9 | 全屏 | 支持 `F11`；**首版保留标题栏（不自动隐藏）**、不设常驻全屏按钮 | 首版不实现顶部浮层与自动隐藏；后续可迭代到沉浸式（见 §5.2） |
| 10 | 子对话框 | 训练/点云/PPOCR/分类**保持原生边框** | 模块只作用于主窗口 |
| 11 | 透明背景/自绘阴影 | **不做**，圆角阴影交给 DWM | 主窗口不启用 `WA_TranslucentBackground` |

### 2.2 对两个疑问的澄清

**“会不会出现两组最小化/最大化/关闭按钮？”——不会。**

- 这是启动时的**二选一**，不是叠加：`frameless=True` 时系统标题栏消失，自绘标题栏及其按钮是唯一一组；`frameless=False` 时**不创建**自绘标题栏，窗口控制完全交给系统。
- 菜单的放法也随之二选一：无边框模式把真实 `QMenuBar` 嵌进标题栏；原生模式把同一个 `QMenuBar` 放回 `QMainWindow` 的标准菜单栏位置。两种模式的菜单 API 相同，因此不会出现“两套菜单”。
- 因为不做运行中切换，不需要“隐藏一组、显示另一组”的复杂状态机，也不需要重新 parent 菜单；这是本次决策带来的主要简化。

**“标题栏按钮范围”那一题问的不是功能清单，而是模块能力。**

之前表述不清楚。它问的是：**通用模块的按钮区要支持到什么程度**，而不是本软件要放哪些按钮。结论应是：

- 模块支持**任意数量、带 key 的按钮**，可分组（左/右）、可排序、可增删；
- 支持文字/图标、可选中（侧边栏显隐）、主次样式、禁用、tooltip、accessibleName；
- 具体放“登录/侧边栏”还是“设置/帮助”由宿主决定，模块不内置任何业务按钮。

## 3. 对外 API 草案

```python
from frameless_window import FramelessWindow, TitleButton

class MainWindow(FramelessWindow):
    def __init__(self):
        super().__init__()
        self.set_app_title("X-AnyLabeling")
        self.set_app_icon(":/images/images/icon.png")

        # 一级菜单：直接返回 QMenu，可继续 addAction / addMenu 做二级菜单
        file_menu = self.add_menu(self.tr("文件"))
        file_menu.addAction(self.actions.open)
        edit_menu = self.add_menu(self.tr("编辑"))
        view_menu = edit_menu.addMenu(self.tr("视图"))  # 二级菜单

        # 标题栏按钮：文字或图标，靠右排列，可指定位置与顺序
        self.add_title_button(
            TitleButton(key="login", text=self.tr("Login"),
                        tooltip=..., role="primary",
                        on_clicked=self.on_login)
        )
        self.add_title_button(
            TitleButton(key="sidebar", icon="panel-left",
                        checkable=True, checked=True,
                        on_toggled=self.toggle_sidebar)
        )

        self.set_content_widget(self._build_central_widget())

        # 窗口形态在构造时确定，不支持运行中切换
        # super().__init__(frameless=True) 或 frameless=False（原生标题栏）
        self.set_resize_margin(6)
        self.set_title_bar_height(30)
```

建议公开的最小接口：

| 接口 | 语义 |
|---|---|
| `FramelessWindow(frameless=True)` | **构造时**决定自绘标题栏（True）或原生标题栏（False）；不提供运行中切换 |
| `set_app_title(text)` / `set_app_icon(path_or_qicon)` | 标题文字与图标；同时同步系统 `windowTitle`/`windowIcon`（任务栏、Alt-Tab 仍正确） |
| `add_menu(title) -> QMenu` | 新增一级菜单，返回可继续扩展的 `QMenu`；三级及以上用 `QMenu.addMenu()` |
| `menu_bar` / `menus` | 暴露内部 `QMenuBar`，供已有代码直接 `addMenu`（降低迁移成本） |
| `set_menu_visible(title, visible)` / `menu_visibility_changed` | 顶层菜单显隐（右键菜单栏勾选），由宿主持久化 |
| `add_title_button(button)` / `remove_title_button(key)` | 标题栏按钮槽位：任意数量、带 key、可左右分组、可选中、主次样式 |
| `set_content_widget(widget)` | 设置中央内容 |
| `toggle_fullscreen()` / `is_fullscreen()` / `fullscreen_changed(bool)` | `F11` 全屏切换与状态（见 §5.2） |
| `maximize/restore/minimize/close` | 窗口控制；同时提供信号 `maximized_changed(bool)` |
| `set_resize_margin(px)` / `set_title_bar_height(px)` | 命中区与标题栏高度 |
| `drag_area` | 允许其他控件注册为可拖动区域（避免菜单/按钮误触发移动） |
| `apply_theme(theme)` | 启动时应用颜色；主题重启生效，不需要运行时重设 |

### 3.1 菜单层级与菜单项形态（补充，2026-11-18）

**结论：菜单层级不设上限，三级及以上菜单与普通菜单一样支持，但必须明确“action 不能嵌 action”这一 Qt 语义。**

- Qt 中 `QAction` 是**叶子节点**，本身不能包含子项；要出现“父项 + 子项”必须使用 `QMenu`。也就是说：
  - 一级：`add_menu("文件")` → 返回 `QMenu`；
  - 二级：`file_menu.addMenu("导入")`；
  - 三级：`import_menu.addMenu("YOLO")`；
  - 第 N 级：`QMenu.addMenu()` 可无限嵌套，模块不需要为层级增加额外 API。
- 若业务希望“一个 action 带子项”，正确写法是把该 action 换成 `QMenu`（`QMenu` 作为菜单项时会自动显示右侧箭头并展开子菜单）；如果确实要给 action 增加“附加信息”而不是子菜单，应使用 `QWidgetAction` 自定义行，而不是层级。
- **动态菜单**必须支持：常见模式是创建空 `QMenu`，在 `aboutToShow` 信号里再 `addAction`（例如“打开最近文件”、类别列表、筛选条件）。模块不得假设菜单在创建时就是静态的。
- 需要覆盖的菜单项形态：普通项、可勾选项、互斥分组（`QActionGroup`）、图标、分隔线、禁用态、快捷键文本、子菜单图标、`QWidgetAction` 自定义行。
- 现有项目已是多层结构，迁移时**不能拍平**：`menus.edit` 通过 `_append_filter_submenus()` 挂“按标签/按组筛选”子菜单，文件列表右键有 `Split` 子菜单，`Open Recent` 也是子菜单；本模块只负责把顶层 `QMenuBar` 嵌进标题栏，子菜单由 Qt 原生弹出。
- 弹层是独立的顶层窗口：三级菜单展开后的样式由 `QMenu` 的 QSS 决定，不在标题栏范围内，主题方案必须同时覆盖 `QMenu`（见 §3.2）。
- 需要注意的边界：
  - 顶层菜单很多（本项目现有 11 个：文件/编辑/视图/主题/语言/上传/导出/工具/工作流/训练/帮助），窄窗口下**折叠为“更多 »”**（已确认），且被折叠的菜单在“更多”里保持完整层级；
  - 顶层菜单可**右键菜单栏空白处**勾选显示/隐藏（已确认）；隐藏的是菜单入口，其 `QAction` 快捷键仍然有效（用户仍可用快捷键），状态由 `set_menu_visible()` 暴露、宿主写入 QSettings；
  - 动态菜单（最近文件、类别列表等）规模按 5 条设计，建议设上限：最近文件默认 5、最多 10，并附“清空列表”；类别类列表超过约 20 条时改用可滚动/可搜索的弹层，而不是纯 `QMenu`；
  - 子菜单贴近屏幕边缘时由 Qt 自动翻转，但若我们给标题栏或弹层加了自绘阴影，需要验证翻转后的位置与阴影不越界；
  - `Alt` 激活菜单、方向键在层级间移动、`Esc` 逐级关闭，依赖 `QMenuBar` 是窗口真正的 menu bar；因此实现上**保留真实 `QMenuBar` 实例**（见 §7 接入路径），不要用一组自绘按钮模拟菜单。

### 3.2 主题、背景色与外观状态（补充，2026-11-18）

**结论：标题栏/菜单栏必须显式定义颜色 token，不能依赖系统默认；因为本项目在浅色模式下全局 QSS 为空。**

现状（核对代码）：

- 主题是 `LIGHT`/`DARK` 两组颜色字典（`theme.py`），字段含 `background`、`surface`、`border`、`text`、`primary` 等；
- `app.py` 在启动时调用 `init_theme()`、`get_dark_palette()`、`get_app_stylesheet()`，分别设置调色板与全局 QSS；
- **`get_app_stylesheet()` 在浅色模式返回空字符串**，因此浅色下 `QMenuBar`、`QMenu` 的颜色来自系统调色板，而不是本项目的 token。这是现成的坑：如果自绘标题栏用 `background` 色，而菜单栏在浅色下仍是系统灰，二者拼在一起会明显分层。
- 深色模式的全局 QSS 已经包含 `QMenuBar`、`QMenu`、`QToolBar`、`QStatusBar` 的配色，可直接复用；浅色模式需要模块自己产出对应 QSS，或由宿主把浅色 QSS 也补齐。
- 当前主题只在启动时应用；设置里改主题是否需要重启，取决于后续实现（现有代码没有运行时重设主题的入口）。模块应提供 `apply_theme(theme)`，由宿主在主题变化后调用，避免“标题栏颜色停在旧主题”。

需要新增/明确的颜色 token（建议全部来自宿主主题字典，不新增独立配置）：

| token | 用途 | 取值建议 |
|---|---|---|
| `titlebar_bg` | 标题栏底色 | 深色用 `background_secondary`，浅色用 `background` 或系统标题栏色 |
| `titlebar_text` | 标题文字 | `text` |
| `titlebar_text_inactive` | 失活窗口标题 | `text_secondary` |
| `titlebar_border` | 标题栏下边线 | `border` |
| `menubar_bg` / `menubar_item_hover` / `menubar_item_pressed` | 菜单栏与悬停/按下 | `titlebar_bg`、`surface_hover`、`surface_pressed` |
| `window_button_hover` | 最小化/最大化悬停 | `surface_hover` |
| `window_button_close_hover` | 关闭按钮悬停 | `error`（红底白字）或系统色 |
| `title_button_primary` | 登录等主按钮 | `primary` / `primary_hover` |
| `menu_bg` / `menu_border` / `menu_selected` / `menu_disabled_text` | 弹出菜单 | 复用现有 `QMenu` 规则 |
| `accent` | 焦点环/选中态（可选） | `highlight` |

必须覆盖的外观状态：

1. **浅色/深色**两套都要有完整取值；不允许“深色好看、浅色拼色”；
2. **窗口激活/失活**：Windows 约定失活标题文字变灰、按钮悬停变淡。Qt 的 QSS 不提供“窗口是否激活”的伪状态，必须在 `WindowActivate`/`WindowDeactivate` 事件里切换标题栏样式类；
3. **按钮状态**：normal/hover/pressed/checked/disabled；关闭按钮 hover 用警示色；
4. **菜单弹层**：背景、边框、圆角、选中项、禁用项、分隔线、勾选图标、图标列宽（现有深色 QSS 已覆盖，浅色需补）；
5. **高对比度/系统强调色**（可选）：跟随系统 `palette().highlight()` 或 Windows 强调色，至少不能出现“白底白字”；
6. **主题运行时切换**：宿主切换主题后调用模块 `apply_theme()`；若暂时只支持重启生效，必须在文档写明，避免出现“标题栏不跟随主题”的 bug 报告。

不建议在标题栏模块里再提供一套独立的“窗口背景色设置”：颜色应统一由主题字典派生，否则会出现主题、菜单、标题栏三套颜色互相打架。

## 4. 子模块划分（建议独立目录/包）

```text
frameless_window/
├── __init__.py          对外导出 FramelessWindow / TitleButton / 常量
├── window.py            QMainWindow 子类：布局、状态、启动模式（无边框/原生）、公开 API
├── title_bar.py         标题栏控件：图标、标题、菜单区、按钮区、窗口控制
├── window_buttons.py    最小化/最大化/关闭按钮与悬停状态
├── hit_test.py          WM_NCHITTEST / startSystemResize 的边缘命中测试
├── window_state.py      最大化/还原、位置尺寸持久化、多屏与 DPI 校正
└── theme.py             高度、圆角、阴影、颜色（可由宿主注入主题）
```

设计约束：

- 只依赖 PyQt6 与标准库，不引入新依赖；
- 不 import 本项目的 `utils`/`config`，主题通过构造参数或 `set_theme(palette)` 注入；
- 模块内部不使用本项目的日志器，使用标准库 `logging`；
- 提供最小可运行示例（`examples/frameless_demo.py`），其他项目复制即可用。

## 5. 关键行为规格（需要逐条确认）

| 行为 | 规格草案 | 备注 |
|---|---|---|
| 拖动 | 标题栏空白区与窗口标题可拖动；按钮/菜单不计入拖动区 | 优先 `QWindow.startSystemMove()`，保留系统贴边吸附 |
| 缩放 | 四边/四角命中 6–8px（按 DPI 缩放），光标形状正确 | `startSystemResize(edges)`；Wayland 可能不可用，需降级 |
| 最大化/还原 | 双击标题栏空白区、按钮、系统快捷键均生效；还原位置正确 | 记录还原前的 geometry，多屏时校验屏幕仍存在 |
| 最小化 | 原生最小化，任务栏恢复正常 | 无边框不影响 |
| 关闭 | 走现有 `closeEvent` 流程（保存、确认、更新清理） | 不绕过现有逻辑 |
| 圆角/阴影 | Windows 11 可由系统 DWM 提供圆角与阴影；无边框后阴影可能消失 | 需要在 Win10 上验证；必要时自绘阴影或放弃阴影 |
| 菜单 | 菜单仍在标题栏内，Alt 激活、方向键、窄窗口折叠行为正常 | 菜单是否允许折行/滚动需定 |
| 快捷键 | 全部 QAction 快捷键不受影响 | 通过菜单/动作继承 |
| 高 DPI | 标题栏高度、按钮尺寸、命中区按 `devicePixelRatio` 缩放 | 需 100%/150%/200% 实测 |
| 多显示器 | 跨屏移动、不同 DPI 拖动、还原位置正确 | 现有 `window/size`、`window/position` 需扩展 |
| 输入法/焦点 | 标题栏不抢焦点；输入法候选框定位正常 | 需实机验证 |
| 可访问性 | 窗口按钮有 accessibleName、可键盘操作 | 原生边框会丢失部分系统语义，需补 |
| 任务栏/Alt-Tab | 图标、标题正常；Win11 Snap Layouts 悬停按钮可能退化 | 退化需在文档声明 |
| 最大化尺寸 | 最大化必须贴合**工作区**而非整屏，任务栏不能被盖住 | Windows 需处理 `WM_GETMINMAXINFO`；否则无边框窗口最大化会覆盖任务栏（常见坑） |
| 系统菜单 | 标题栏右键或 `Alt+Space` 弹出移动/大小/最小化/关闭 | 无边框后系统菜单默认消失，需显式实现 |
| 从最大化拖动 | 按住标题栏拖动最大化窗口时，先还原到合适尺寸并继续拖动 | 原生行为，需要模拟，否则用户会觉得“卡住” |
| 键盘窗口操作 | `Win+←/→/↑` 贴边、`Alt+F4`、`Alt+Space`、`F10`/`Alt` 激活菜单 | 依赖 `WS_THICKFRAME` 与 `WM_NCHITTEST`，只用 `startSystemResize` 可能失效 |
| 全屏 | `F11` 或代码全屏进入/退出，与最大化互斥，退出后恢复原状态 | 是否支持需确认 |
| 激活/失活外观 | 标题文字与按钮随窗口激活状态变化 | QSS 无对应伪状态，需事件切换样式类 |
| 拖动性能 | 拖动时不得整窗重绘卡顿，优先系统级移动 | 画布较大时需实测 |
| 透明背景 | 主窗口默认不使用 `WA_TranslucentBackground`，圆角/阴影优先交给 DWM | 透明背景与 OpenGL/视频子窗口、渲染性能存在冲突 |
| 菜单溢出 | 顶层菜单放不下时折叠为“更多 »”，不挤压标题栏按钮 | 本项目现有 11 个顶层菜单，必须定策略 |
| 子窗口 | 训练/点云/PPOCR/分类等 `QDialog` 保持原生边框 | 避免“主窗口无边框”牵连所有对话框 |

- 初版最关键的漏项是 **最大化工区、系统菜单、键盘贴边、激活态外观**——这四项不做，无边框窗口会在日常使用中明显“不像原生窗口”。

## 5.2 全屏（F11）方案（2026-11-18 建议稿）

**参考惯例**（通用经验，不逐条断言具体产品行为）：桌面类工具（文件管理器、编辑器、浏览器）普遍用 `F11` 切换全屏，不提供常驻的全屏按钮；只有视频/演示类软件才把全屏做成显式按钮。标注工具属于前者，建议**不加常驻全屏按钮**。

**首版决定（2026-11-18）**：采用下面的“保留标题栏”方案；沉浸式自动隐藏作为后续迭代，不在首版范围。

**后续迭代方案（沉浸式，非首版）**

1. `F11` 进入/退出全屏；默认不新增全屏按钮。模块保留 `add_title_button`，宿主以后想加随时可加。
2. 进入全屏时：记录当前状态（普通/最大化）与 geometry；隐藏自绘标题栏、菜单栏与窗口控制按钮；窗口覆盖整块屏幕（含任务栏区域）。
3. 鼠标移到屏幕顶部边缘时浮出半透明标题条（软件名 + 退出全屏按钮），移开后自动隐藏；这样不需要常驻按钮。
4. 退出全屏：恢复进入前的状态与 geometry；若进入前是最大化，恢复为最大化。
5. 状态机：普通 ↔ 最大化 ↔ 全屏三态互斥；全屏下调 `maximize()` 先退出全屏；全屏下双击标题栏无效（标题栏已隐藏）。
6. **不持久化全屏状态**：重启回到普通/最大化，避免“开机即全屏”的意外。
7. `Esc` **不**退出全屏（画布已用 `Esc` 取消绘制/退出编辑），退出只靠 `F11` 或顶部浮层按钮。
8. 其他约束：Alt+Tab/任务栏切换后保持全屏；多屏时全屏落在当前屏幕；DPI 变化后重算浮层命中区。

**首版方案（2026-11-18 已确认，保留标题栏）**：`F11` 只做无边框全屏，标题栏与菜单栏保持可见（不自动隐藏），窗口按钮仍可用。沉浸感弱，但没有浮层与自动隐藏的复杂度；后续可迭代到上面的沉浸式方案。

## 6. 平台差异与降级

- **Windows 10/11**：主目标。用 `nativeEvent` 处理 `WM_NCHITTEST` 可保留缩放、贴边、Snap；若只用 `startSystemResize`，Win11 的 Snap Layouts 悬停提示可能丢失。另需处理：
  - `WM_GETMINMAXINFO`：最大化贴合工作区，不覆盖任务栏；
  - `WS_THICKFRAME`（或命中测试等价实现）：`Win+←/→/↑` 与系统贴边才生效；
  - `DWMWA_USE_IMMERSIVE_DARK_MODE`：深色主题下系统边框/阴影不发白；
  - `WM_NCHITTEST` 对按钮区返回 `HTCLIENT`，否则按钮点不动；
  - `AppUserModelID`：任务栏图标分组正确。
- **Linux X11**：默认无边框（已确认）。用 `startSystemMove/Resize`，但窗口管理器（GNOME/KDE/XFCE）差异大；需保留“启动配置切回原生”的兜底。
- **Wayland**：默认无边框（已确认），但客户端无法自行定位/移动，`startSystemMove` 支持视合成器而定；必须在文档声明“部分合成器下拖动/缩放可能不可用”，并保留配置回退。
- **macOS**：默认无边框（已确认）。但无边框会失去交通灯按钮语义、且菜单默认合并进系统全局菜单栏，自绘标题栏收益有限；若实现中出现全局菜单冲突或全屏行为异常，建议在 macOS 上退为原生标题栏（“透明标题栏”样式作为折中）。这一条需要实机验证后再定。
- 回退方式：**启动配置二选一**（`frameless=True/False` 或配置文件/环境变量），不提供运行中切换；`nativeEvent` 处理出现异常时应自动回退到原生边框，而不是让窗口失控。

## 7. 接入本项目的改动清单（重点）

推荐接入路径（成本最低）：**保留 `QMainWindow` 与 `QToolBar`，用 `setMenuWidget(title_bar)` 把自绘标题栏放进菜单栏区域，标题栏内部嵌入一个真实的 `QMenuBar`，并让 `MainWindow.menuBar()` 返回这个实例。** 这样现有 `LabelingWidget` 里 `self.parent.parent.menuBar().addMenu(...)` 的用法基本不变。

| 模块/位置 | 现状 | 需要改动 | 工作量 |
|---|---|---|---|
| `views/mainwindow.py` | 原生 `QMainWindow` + `menuBar()` + `QToolBar` 停靠 + status bar + `window/size`、`window/position`、`window/toolbar_area` 持久化 | 继承 `FramelessWindow`；新增标题栏与菜单嵌入；`menuBar()` 覆写；窗口状态增加 `window/maximized`；启动时按配置选择是否自绘标题栏（不做运行中切换）；WSL 特判保留 | 中 |
| `views/labeling/label_widget.py` | `menu()` 用 `self.parent.parent.menuBar()` 建菜单；`menus.edit/view/...`；`update_progress_title()` 调 `setWindowTitle`；`self.tools` 为 `QToolBar`；`populate_mode_actions()` 组装右键菜单 | 菜单构建大概率**不用重写**（仍用 QMenuBar）；但标题显示改为标题栏 API；`setWindowTitle` 调用点需统一；若标题栏空间有限，需定义标题截断策略 | 小–中 |

| `views/labeling/utils/style.py` | 主题色、按钮/面板样式 | 增加标题栏/窗口按钮样式；需跟随主题与 DPI | 小 |
| `views/labeling/utils/qt.py` | `new_action`/图标 | 不变 | 无 |
| `app.py` | 启动、图标、翻译 | 设置 AppUserModelID/窗口图标；无边框开关读取命令行或配置 | 小 |
| `label_widget` 的 CornerWidget（fork.6 的 `OperatorBar`） | 已在菜单栏右上角 | 迁移到 `add_title_button`，接口不变 | 小 |
| `update_controller`、各 `QDialog` | 模态、父子关系 | 一般不变；需验证无边框下模态遮罩、居中、阴影 | 回归 |
| `Settings` / `QSettings` | `window/size`、`window/position`、`window/toolbar_area`、`window/toolbar_visible` | 新增 `window/maximized`、`frameless/enabled`（启动配置）、`frameless/menu_visibility`；旧键兼容与迁移；最大化状态下退出再启动需正确还原 | 中 |
| 新增 `anylabeling/widgets/frameless/` | 当前不存在该包 | window/title_bar/window_buttons/hit_test/window_state/theme 六个模块 + `__init__` 导出；只依赖 PyQt6 与标准库 | 中 |
| 测试 | 以 widget 单测为主 | 新增几何/命中/菜单显隐/全屏状态机/启动模式切换测试；Windows 行为需实机验证（当前环境无法 GUI 回归） | 中 |

明确**不需要重写**的部分：`Canvas`、`Shape`、`LabelFile`、自动标注、训练/导出、点云/PPOCR 等业务模块与菜单内容；`QToolBar` 本身也不需要重写，除非选择“把工具栏并入标题栏”的激进方案。

**风险最高的五处**：

1. 最大化/还原与多屏 DPI：现有代码只保存 `size/position`，最大化状态、跨屏还原需要重做并实机验证；
2. 工具栏停靠：历史上出现过“浮动工具栏恢复导致窗口尺寸爆炸”的问题（见 `mainwindow.py:85-141` 注释），无边框后拖拽与停靠的交互需重新回归；
3. 菜单嵌入标题栏：`Alt` 激活、菜单折行、与拖动区的冲突；
4. **原生行为补齐**：最大化工区、系统菜单、键盘贴边、激活态外观属于平台消息处理，缺失时会明显“不像原生窗口”（见 §5.1）；
5. **浅色主题配色**：全局 QSS 在浅色模式为空，标题栏与菜单栏必须显式配色，否则出现分层/拼色（见 §3.2）。

4. **全屏**：首版保留标题栏（按 §2.1 决策），沉浸式自动隐藏未实现。
5. **未实机验证**：Windows 的拖动/缩放/贴边/最大化工区，以及 macOS/Wayland 形态，仍需实机确认。
6. **`nativeEvent` 的硬约束**：覆写中**不得**调用 `super().nativeEvent()`；PyQt6 在 Windows 上会重入并崩溃（fork.7 启动闪退的根因），未处理路径必须返回 `(False, 0)`。fork.8 已修复并加回归用例。
7. **边缘缩放需要 `WS_THICKFRAME`**：仅返回 `WM_NCHITTEST` 的 `HT*` 不够；fork.9 在 `showEvent` 补该样式并用 `WM_NCCALCSIZE`（返回 0）收回客户区。高 DPI 下 `WM_NCHITTEST` 坐标需按 `devicePixelRatio` 换算。

验证与限制详见 `CHANGELOG-fork.md` 的 fork.7 记录。
