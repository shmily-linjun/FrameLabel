## 一、项目背景与目标

1. 本项目是 X-AnyLabeling 4.3.2 的私有 fork，目标是持续演进为自用的工业视觉数据平台。
2. 对标 HandleAI/AIDI、Intel Geti、CVAT、Label Studio 等产品，吸收适合本项目的功能与交互设计，不机械照搬。对不熟悉或无法确认的产品能力，不得编造。
3. 最终形成“标注、训练、调优、评估”等能力，各模块深度解耦：
   - 外部标注数据可以绕过本软件标注模块，直接进入训练或评估流程。
   - 外部训练得到的模型或预测结果，可以独立进入本软件评估流程。
   - 各模块通过明确的数据格式、接口和模型工件契约协作，而不是依赖界面调用或隐式全局状态。
4. 总体架构采用 Model-View-Controller。工厂、单例、生产者消费者、插件等模式按实际需要采用，不为使用设计模式而增加复杂度；尤其避免单例导致的全局状态、隐藏依赖和测试困难。
5. 项目以持续可用、可维护、可测试、可移交为目标，避免无关重构、过度设计和一次性“大跃进式”改造。

## 七、临时文件与删除安全

1. 测试、调试和验证产生的**所有无法跨任务重复使用的文件和目录**必须放在仓库根目录的 `temporary` 中。开始运行前建立任务或进程专属目录，不得先写入仓库根目录再移动，也不得未经说明和授权改用系统临时目录绕过配置或权限问题。
2. pytest 默认由 [tests/conftest.py](../tests/conftest.py) 为每次运行创建 `temporary/runs/pytest-<PID>-<随机值>/`：
   - `tmp_path`、`tmp_path_factory` 等 pytest 临时 fixture 使用本次运行目录下的 `fixtures`；显式传入 `--basetemp` 时必须使用该次运行专属的新路径，不得复用其他任务目录。pytest 会删除已有的显式 `basetemp`，禁止把共享父目录或 `temporary` 本身传给它。
   - 直接调用 `tempfile` 的代码及测试子进程使用本次运行目录下的 `process`；通过测试进程内的 `TEMP`、`TMP`、`TMPDIR` 和 `tempfile.tempdir` 统一指定，不修改全局环境。新增测试工具或被测子进程时，必须检查其实际临时路径是否继承该约束。
3. 可复用缓存与一次性文件分开管理。pytest 缓存固定为 `temporary/cache/pytest`，由 `pyproject.toml` 的 `cache_dir` 配置；需要复用时不得每次更换路径。确不使用缓存时可传 `-p no:cacheprovider`，但涉及缓存功能的测试不得借此跳过验证。
4. 其他测试、调试和验证工具的一次性产物也应显式定向到本次任务目录；不得仅重定向 pytest 就默认所有工具均已遵守。若工具仍写入根目录或其他未授权位置，应停止重复运行，记录实际路径和生成工具，先解决工具级配置问题。

## 八、文档、版本号与 Git

1. 严格控制新增 Markdown 文档。创建新 md 文件前，先说明现有文档为何不适合承载，并询问是否有必要新增。
2. 文档优先合并到现有文档；避免内容重复、职责不清和文档泛滥。
3. 每次经授权的需求修改完成并验证后，必须更新相关现有文档和 CHANGELOG-fork.md，并提交 Git。fork 版本号按以下标准判定，**不得仅因发生代码修改、提交次数或任务名称而机械升版**：
   - 满足至少一项时，必须升级一次 fork 版本号：
     - 用户可观察的功能或行为变化，包括新增/删除功能、缺陷修复、操作流程、默认行为、CLI 参数或输出结果变化；
     - 调用方需要适配的接口或契约变化，包括公共 API、配置键及语义、标注/数据格式、模型工件、数据库结构、worker payload/事件协议；
     - 依赖版本、支持平台、运行环境或兼容性要求变化，或需要数据迁移、兼容分支、发布说明提醒用户。
   - 下列情况不升级 fork 版本号：
     - 纯文档、注释、测试用例、示例、格式化、排版、资源文件移动，以及不改变运行行为的内部重构；
     - 日志、翻译、文案或样式微调，只要不改变操作结果、接口含义或兼容性；
     - 仅改善内部可读性、测试稳定性或静态检查，且不改变外部可观察行为。
   - 判定时看实际影响而非代码行数：一行缺陷修复仍须升版，大规模但无行为变化的重构也不升版。难以判定时，先列出修改前后的行为差异并询问，**不得默认升版**。非升版改动可将补充说明记入当前 fork 版本的变更记录，并使用 `docs`、`chore`、`test`、`refactor` 等相符的提交类型。
4. 同一提交批次中的多个需求最多升级一次 fork 版本号；其中只要有一项满足升版标准才升级，不因需求数量或提交数量重复递增。版本号沿用项目现有规则；规则不明确时先询问，不自行发明。
5. **累积改动的默认递增阈值**：先排除上述不需要递增版本的改动，再统计自上一个 fork 版本以来尚未纳入版本的改动；当独立改动点 **≥3 个**且涉及 **≥2 个模块**时，应递增一次 `fork.N`。两个条件必须同时满足。
   - “独立改动点”应能分别说明目的、审查行为变化、验证结果和回退影响；同一个问题的多处配套修改算一个改动点。
   - 同一机械性修改在多个文件中的重复应用只算一个改动点，不按文件、行数或提交次数计数。
   - “模块”按[结构报告](dev/CODE_STRUCTURE_REPORT.md)的职责边界判断，不以文件数量代替。
   - 达到阈值后仍只递增一次，不按照改动点数量连续跳号；纯文档等已明确豁免的改动不适用此阈值。
6. CHANGELOG-fork.md 和 Git commit message 应详细记录：
   - 修改背景与原因；
   - 主要实现和关键细节；
   - 涉及的模块及文件；
   - 行为、接口和兼容性影响；
   - 实际验证内容；
   - 已知限制或后续事项。
7. 提交前必须：
   - 清理本次产生的临时文件；
   - 检查 git status、git diff 和暂存内容；
   - 确认没有混入无关修改、缓存、日志、测试数据、模型权重或敏感信息；
   - 确认版本号和 CHANGELOG-fork.md 已同步更新。
8. Git 提交与推送按是否升级 fork 版本号区分：
   - **升级 fork 版本号时，完成验证并形成包含版本号、CHANGELOG-fork.md 和相关文档的完整提交后，必须自动将当前分支 push 到云端 GitHub 对应远程分支。**这是持续授权，无需每次另行询问；只能普通 push，禁止 force push。推送前核对远程仓库、当前分支和上游跟踪关系，推送失败时报告本地提交哈希与错误，不得声称云端已更新。
   - 不升级 fork 版本号的小改动默认只在本地 Git 提交，不自动 push；我明确要求推送时除外。
   - 无远程仓库、上游配置异常或验证/提交前检查未通过时，不得推送；先报告并处理阻塞项。
9. 如果验证失败或修改范围存在疑问，不得为了完成流程而提交，应先报告问题。

## 十、标注归属与操作员契约（fork.4 起）

1. XLABEL JSON 顶层新增可选字段 `author`（操作员名称，或 `"none"` 表示未记录）与 `modified_at`（本机 ISO 8601，含 UTC 偏移）。仅当标注内容、flags、tags、description、relations 实质变化时更新；`checked`、`split` 变化不更新；旧文件、导入/转换数据一律为 `none`，不反推文件时间。字段缺失按未记录处理，旧数据无需迁移。
2. 操作员账号库是**应用级**存储，位于与 `--work-dir` 无关的系统应用数据目录：Windows `%APPDATA%\X-AnyLabeling\operators\operators.db`，Linux `$XDG_DATA_HOME/X-AnyLabeling/...`（缺省 `~/.local/share`），macOS `~/Library/Application Support/X-AnyLabeling/...`。它随软件/机器走，不是项目数据库，不随项目分发，也不被项目数据库引用；旧路径 `<work_dir>/xanylabeling_data/operators/operators.db` 仅作为首次迁移来源（复制，不删除）。项目数据库不得依赖账号库或登录状态才能打开与标注。
3. 归属是**数据级**事实，`author` 是 T3 之前的过渡载体。T3 落地时 `annotation_revision.editor` 以名字字符串记录操作者、不建外键；迁移导入原样带入 `author`，不得用当前登录者覆盖；一期如需冗余 `last_operator`，语义必须与 JSON 一致。详见讨论稿 §12A 与设计书 §3.4。
4. 账号与登录只用于身份记录与操作门禁，**不构成安全边界**，不得在文档或界面中表述为防篡改、防抵赖或权限体系；多租户/复杂权限仍属长期候选（设计书 §2）。
5. 专项工作区（点云、PPOCR、VQA、图像分类、视频分类）当前不在归属与门禁范围内；扩大范围需单独授权。
