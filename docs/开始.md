## 一、项目背景与目标

1. 本项目是 X-AnyLabeling 4.3.2 的私有 fork，目标是持续演进为自用的工业视觉数据平台。
2. 对标 HandleAI/AIDI、Intel Geti、CVAT、Label Studio 等产品，吸收适合本项目的功能与交互设计，不机械照搬。对不熟悉或无法确认的产品能力，不得编造。
3. 最终形成“标注、训练、调优、评估”等能力，各模块深度解耦：
   - 外部标注数据可以绕过本软件标注模块，直接进入训练或评估流程。
   - 外部训练得到的模型或预测结果，可以独立进入本软件评估流程。
   - 各模块通过明确的数据格式、接口和模型工件契约协作，而不是依赖界面调用或隐式全局状态。
4. 总体架构采用 Model-View-Controller。工厂、单例、生产者消费者、插件等模式按实际需要采用，不为使用设计模式而增加复杂度；尤其避免单例导致的全局状态、隐藏依赖和测试困难。
5. 项目以持续可用、可维护、可测试、可移交为目标，避免无关重构、过度设计和一次性“大跃进式”改造。

     - 纯文档、注释、测试用例、示例、格式化、排版、资源文件移动，以及不改变运行行为的内部重构；

     - 仅改善内部可读性、测试稳定性或静态检查，且不改变外部可观察行为。
   - 判定时看实际影响而非代码行数：一行缺陷修复仍须升版，大规模但无行为变化的重构也不升版。难以判定时，先列出修改前后的行为差异并询问，**不得默认升版**。非升版改动可将补充说明记入当前 fork 版本的变更记录，并使用 `docs`、`chore`、`test`、`refactor` 等相符的提交类型。

## 十、标注归属与操作员契约（fork.4 起）

1. XLABEL JSON 顶层新增可选字段 `author`（操作员名称，或 `"none"` 表示未记录）与 `modified_at`（本机 ISO 8601，含 UTC 偏移）。仅当标注内容、flags、tags、description、relations 实质变化时更新；`checked`、`split` 变化不更新；旧文件、导入/转换数据一律为 `none`，不反推文件时间。字段缺失按未记录处理，旧数据无需迁移。
2. 操作员账号库是**应用级**存储，位于与 `--work-dir` 无关的系统应用数据目录：Windows `%APPDATA%\X-AnyLabeling\operators\operators.db`，Linux `$XDG_DATA_HOME/X-AnyLabeling/...`（缺省 `~/.local/share`），macOS `~/Library/Application Support/X-AnyLabeling/...`。它随软件/机器走，不是项目数据库，不随项目分发，也不被项目数据库引用；旧路径 `<work_dir>/xanylabeling_data/operators/operators.db` 仅作为首次迁移来源（复制，不删除）。项目数据库不得依赖账号库或登录状态才能打开与标注。
3. 归属是**数据级**事实，`author` 是 T3 之前的过渡载体。T3 落地时 `annotation_revision.editor` 以名字字符串记录操作者、不建外键；迁移导入原样带入 `author`，不得用当前登录者覆盖；一期如需冗余，统一为 `editor`/`modified_at`，语义必须与 JSON 一致。详见讨论稿 §12A 与设计书 §3.4。
4. 账号与登录只用于身份记录与操作门禁，**不构成安全边界**，不得在文档或界面中表述为防篡改、防抵赖或权限体系；多租户/复杂权限仍属长期候选（设计书 §2）。
5. 专项工作区（点云、PPOCR、VQA、图像分类、视频分类）当前不在归属与门禁范围内；扩大范围需单独授权。
